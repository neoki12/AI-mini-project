# 완성차 공장 4M 변경 영향 검토 Agent 결과 보고서

###SKALA 광주 2반 G047 김현수


4M 변경 요청을 받아 필요한 검증 항목, 변경 등급, 다음 공정 영향을 근거와 함께 정리하는 Multi-Agent 시스템을 만들었다. 개선 기능을 모두 끈 Baseline과 모두 켠 Improved를 같은 코드로 비교하면 F1은 0.27에서 1.00으로 올랐다. 개발 중 쓰지 않은 표현에서는 0.92~0.98로, 분류가 약점으로 남았다.

## 1. 개요

### 1.1 문제 정의

- 완성차 공장에서 작업자(Man), 설비(Machine), 재료(Material), 공법(Method)이 바뀌면 품질 담당자가 필요한 검증 항목을 정해야 한다. 이 일은 담당자의 경험에 크게 의존해 항목이 빠지기 쉽다.
- 한 공장의 변경이 다음 공장에 주는 영향은 공장별 체크리스트로는 드러나지 않는다.
- LLM에 그대로 물으면 근거 없는 항목을 만들거나 필수 항목을 빠뜨린다.

목표는 변경 요청 하나에 대해 필요한 검증 항목을 빠짐없이 도출하고 모든 항목에 근거를 다는 것이다. 최종 판단은 품질 담당자가 하고, Agent는 누락을 막는 검토 보조 역할을 한다. 공장, 표준서, 설비 데이터는 실제 공장 구조를 참고해 만든 교육용 가상 데이터다.

### 1.2 기존 시스템의 문제와 해결 과제

| Base의 문제 | 해결 과제 |
|---|---|
| 검증이 3회 실패하면 강제로 통과 | "추가 확인 필요"로 내보내고 이유를 표시 |
| 형식만 검사해 항목 누락과 잘못된 인용을 모름 | 항목 누락과 근거 인용을 코드로 검사 |
| LLM이 빠뜨린 필수 항목을 되살릴 수 없음 | 규칙표의 필수 항목을 강제로 추가하는 권위 게이트 |
| 벡터 검색, 평가, 테스트가 없음 | RAG, Baseline/Improved 평가, LLM-as-a-Judge, 테스트와 CI |

## 2. 적용 기술

![시스템 구조](report_images/architecture.png)

*그림 1. 시스템 구조. 파란 칸은 LLM을 쓰는 단계, 흰 칸은 코드 규칙으로 처리하는 단계다.*

요청 한 건은 다음 순서로 처리된다. Router가 4M 변경 요청인지 확인하고, Classifier가 공장과 변경 유형을 판별한다. Planner가 조사 계획을 세우면 권위 게이트가 빠진 필수 항목을 채운다. Research는 표준서 검색과 설비, 라인 상태 조회를 병렬로 실행하고, Judge가 조건부 항목의 해당 여부를 판정한다. Assessor가 체크리스트와 등급을 정하면 Writer가 보고서를 쓰고, Validator가 누락과 인용 오류를 검사한다. 근거가 부족하면 Research로, 검증에 실패하면 Writer로 돌아간다.

| 기술 | 적용 내용 |
|---|---|
| Multi-Agent, LangGraph | Supervisor 패턴으로 분류, 계획, 조사, 판정, 작성, 검증을 전문 Agent로 나눠 호출. 근거가 부족하면 재조사하고 검증에 실패하면 다시 쓰는 동적 재계획 |
| MCP | 설비와 라인 상태 Tool, 표준서 Resource, 검토 Prompt. 연결이 끊기면 자동 재연결 |
| RAG | 표준서 41개 조항을 `bge-m3`로 임베딩해 Chroma 벡터 DB에 저장하고, 공장과 변경 유형으로 걸러 의미 검색한 조항을 판정과 보고서 작성에 근거로 넣음 |
| 모듈화와 의존성 주입 | Agent별 모듈로 분리하고 모든 노드에 LLM, MCP, 기능 스위치를 주입. 스위치만 바꿔 같은 코드로 Baseline을 만듦 |
| 테스트 | 단위와 통합 테스트, 화면 E2E 테스트 174개를 GitHub Actions CI에서 실행 |
| 관측과 평가 | LangSmith 추적과 사용자 피드백, 평가 실험. 별도 LLM이 보고서를 채점하는 LLM-as-a-Judge |
| 기타 | FastAPI REST API, SSE 실시간 스트리밍, Vue 3 화면, SQLite 이력 저장, 동시 실행 제한과 대기열 |

핵심 원칙은 **규칙으로 정해지는 것은 코드가, 판단이 필요한 것만 LLM이** 맡는 것이다. LLM은 주로 분류, 계획, 조건 판정, 보고서 작성에 쓴다.

## 3. 구현 결과

### 3.1 개선 포인트

| 개선 | 해결한 문제 | 효과 |
|---|---|---|
| 권위 게이트: 규칙표의 필수 항목을 코드가 강제로 넣는 단계 | LLM 계획에서 필수 항목 누락 | 필수 항목 Recall 0.14 → 1.00 |
| 현장 데이터 연동 | 문서만으로는 설비 이상을 모름 | 현장 항목 Recall 0.00 → 1.00 |
| 공정 간 영향 | 다음 공장 확인 항목 누락 | 다음 공정 Recall 0.00 → 1.00 |
| 등급 판정 | 안전 체결부를 놓쳐 승인 절차 생략 | 등급 정확도 0.90 → 1.00 |
| 안전장치 | 관련 없는 입력, 공장 추측 | 분류 정확도 0.80 → 1.00, 모르면 되묻기 |

### 3.2 시연: 같은 요청, Baseline vs Improved

"차체 대시 패널 라인 용접 로봇(BD-RB-301, BD-RB-302)의 용접 전류 조건을 변경합니다."라는 요청의 정답 검증 항목은 9개다. Baseline은 1개만 찾고도 "검토 완료"로 내보냈고, Improved는 9개를 모두 찾았다. 필수 항목은 권위 게이트가, 로봇의 팁 교체 주기 초과는 MCP Tool이 찾아냈다.

## 4. Before/After 실측 비교

같은 코드에서 개선 기능만 끈 Baseline과 켠 Improved를 평가 10건으로 3회씩 비교했다. 모델은 Ollama `qwen2.5:7b`, `qwen3:8b`와 OpenAI `gpt-4o-mini`, `gpt-4o`를 썼다. F1은 시스템이 낸 검증 항목을 정답 목록과 비교해, 빠뜨린 정도를 보는 Recall과 잘못 넣은 정도를 보는 Precision을 함께 반영한 점수다.

| 지표 | Ollama Baseline | Ollama Improved | OpenAI Baseline | OpenAI Improved |
|---|---|---|---|---|
| F1 | 0.268 | 1.000 | 0.283 | 0.997 |
| 평균 지연 | 24.6초 | 41.6초 | 4.3초 | 9.0초 |

- 두 모델 모두 F1이 약 0.7 올랐다. 향상은 모델이 아니라 구조에서 나왔다.
- **홀드아웃**: 개발 중 쓰지 않은 표현 10건에서는 F1 0.92~0.98이었다. 가장 큰 약점은 분류였고, 틀린 사례도 모두 "검토 완료"로 나갔다.
- **LLM-as-a-Judge**: Ollama로 만든 보고서를 gpt-4o가 채점한 근거 충실도는 Baseline 0.70, Improved 0.90이었다. 지어낸 조항을 넣으면 판사가 10건 모두 찾아냈지만, 정답 등급을 틀렸다고 본 오판도 1건 있어 규칙 채점의 보완용으로만 쓴다.

## 5. 교훈

### 5.1 한계와 트레이드오프

- 정확도를 얻은 대가로 지연이 1.7~2.1배 늘었다.
- 모르면 되묻고 불확실하면 항목을 넣는 설계는 누락을 막는 대신 사람의 확인 부담과 과잉 항목을 늘린다.
- 확신을 갖고 틀린 경우는 걸러내지 못한다.
- 평가 10건, 가상 표준서 9종의 개념 증명 수준이다.

### 5.2 향후 개선

- 키워드와 LLM의 분류가 다르면 "추가 확인 필요"로 돌려 확신 있는 오답 걸러내기
- 등급별 승인 워크플로와 실제 MES 연동
- 평가 데이터 확대와 판사 점수의 사람 평가 비교

### 5.3 수행 소감

처음에는 프롬프트를 잘 다듬으면 LLM이 검증 항목을 찾아 줄 거라고 생각했다. 하지만 LLM에 그대로 맡기니 9개 중 1개만 찾고도 "검토 완료"라고 답했다. 규칙은 코드에, 판단은 LLM에 나눠 맡기자 두 모델 모두 거의 같은 폭으로 좋아졌고, "어떤 모델을 쓰느냐"보다 "LLM에게 무엇을 맡기느냐"가 중요하다는 것을 배웠다.

개발 데이터에서 1.0이 나왔을 때는 기뻤지만, 처음 보는 표현으로 다시 재니 점수가 떨어지고 틀린 사례가 "검토 완료"로 나갔다. 점수보다 어디서 틀리는지가 더 중요한 정보였고, 만점일수록 의심해야 한다는 것을 느꼈다.

## 6. 결론

규칙으로 정할 것은 코드가, 판단이 필요한 것만 LLM이 맡는 구조로 검증 누락을 막는 검토 보조 Agent를 만들었다. F1은 0.27에서 1.00으로 올랐고, 다음 과제는 확신 있는 오답을 걸러내는 것이다.
